## 1. Decision note: Supabase, not iCloud

The owner has decided:
- After 1.0, **Supabase (project `xukhlkjjrrwmorxtlizh`) is the single source of truth** for a signed-in user's poker data.
- **iCloud / CloudKit sync (#10) is cancelled.**

Why: the 1.2 web app and the 1.3 leaderboards need data on a server the team controls.

What this costs users, and how the spec handles it:
- **Privacy.** Data lives on PokerStats' servers, not in the user's own iCloud. See section 11 for copy that says this honestly.
- **Offline.** The app must stay fully usable offline. See section 7.
- **Accounts.** Sync needs a PokerStats account. Users who never sign in keep a local-only app. See section 3.

---

## 2. Problem

Today a signed-in user's data is protected only by **whole-database backups**:

- After a session ends or is abandoned, the app uploads one compressed snapshot of everything to `backups/{userId}/` in Supabase Storage. A row in `backup_metadata` describes each snapshot, and the last 5 are kept.
- On a device whose local data is empty, the latest backup is restored automatically, once per device (`AutoRestore`, `AutoRestoreFlag`). Delete All Data turns that auto-restore off.
- Restore replaces everything in one save (`LocalDataRestorer`).

That design can't support 1.1 and later:

1. **Two iPhones overwrite each other.** Each backup is a full snapshot. If two devices both back up, the newest snapshot silently wins and the other device's sessions are dropped from the cloud copy.
2. **No web, no leaderboards.** A compressed snapshot can't be read or queried per session or per hand.
3. **Work since the last backup can be lost.** Backups only run at session end, so hands logged in a session that never ended (crash, lost phone) aren't in the cloud.
4. **Restore is all-or-nothing.** There is no merge, so the app only auto-restores into an empty device.
5. **Two known risks** have to be designed out, not carried forward:
   - Delete All Data leaves cloud backups behind (#77).
   - Signing out leaves local data that the next account could upload (#69).

| Group | Today | In 1.1 |
|---|---|---|

| Signed in, no backups yet | Data on device only | Local data uploaded on first sync |
| Never signed in | Data on device only; the app works fully without an account | **Unchanged.** Local-only, no sync, nothing leaves the device. A "Turn on Sync" entry point offers sign-in. |

## 4. Goals and non-goals

### Goals
1. A signed-in user's sessions, hands and settings are the same on every iPhone they sign in to, and in the 1.2 web app.
2. Everything works offline. Logging a hand never waits for the network, and the under-3-second logging promise holds.
3. Users never silently lose data to sync. Conflicts resolve predictably, and anything destructive is explicit and labeled.
4. Existing backup users move over without doing anything, and without duplicate sessions.
5. Data is private to its owner by default. Nothing is visible to other users.
6. Delete All Data and Delete Account behave correctly and clearly once data exists on several devices and the server (App Review 5.1.1(v)).
7. Stats (P/L, hourly rate, VPIP and the rest) show the same numbers on iOS and web for the same data.
8. The data model leaves room for tournament sessions (#8) without another migration of user data.

### Non-goals for 1.1
- Sharing sessions or stats with other people (separate 1.1 sharing spec).
- Leaderboards (1.3).
- The web app itself (1.2).
- Google Sign-In (1.2) and account linking or merging two accounts.
- iPad or Mac apps (the app is iPhone-only today).
- End-to-end encryption (it would block web and leaderboards). Open question 8.
- Real-time co-editing of one active session from two devices (section 8 defines a simpler rule).
- Detecting duplicate sessions a user typed in twice by hand.
- CSV/JSON export (#9). Separate feature, though sync makes it easier.
- Tournament features themselves (#8). Only the room for them is in scope.

## 5. User stories

1. As a player with two iPhones, I log a session on one and see it, with all hands, on the other within a minute of both being online.
2. As a player in a casino with no signal, I start a session, log 200 hands, end it, and everything syncs later without me doing anything.
3. As a player who edited the same session's notes on both phones, I end up with one clear result and know when another device changed something I was looking at.
4. As a player who deletes a session on one phone, it's gone everywhere, and I can get it back for a while if it was a mistake.
5. As an existing backup user, I update to 1.1 and my data is simply there and syncing. I don't have to restore anything, and nothing is duplicated.
6. As a player setting up a new phone, I sign in and my full history appears, including on a phone that already had a few local sessions.
7. As a player who has never signed in, the app keeps working exactly as before, and I can turn sync on later without losing anything.
8. As a privacy-minded player, I know my data is visible only to me, and the app tells me plainly where it's stored.
9. As a player deleting my account, everything is removed from the server and my devices, and the app tells me what happens on my other phone.
10. As a player who later uses the web app, the numbers on the web match the numbers on my iPhone.

## 6. What syncs

All synced data belongs to exactly one account and is readable and writable only by that account (and by the service operator, see section 11).

| Data | Syncs | Notes |
|---|---|---|
| **Sessions** | Yes | Every field: start and end time, location, game type, stakes, notes, status (including active), buy-in, rebuys, add-ons, cash-out, tips (`tipRake`), tilt, energy and focus levels. |
| **Hands** | Yes | Every field: hand number, timestamp, preflop action, 3-bet facing and response, postflop result, c-bet, notes, position. Linked to their session. |
| **Settings** | Yes, one set per account | Default game type, stakes, buy-in, currency. |
| **Table setups** (auto-position config on a session) | Yes, with its session | Includes seat names, which are **other people's names** typed by the user. Open question 4. |
| **Stack checks** (#30, planned) | Yes, once #30 ships | Each check is its own synced record linked to the session. #30 builds on the 1.1 sync data, not on a new backup format. |
| **Tips and add-ons** (#27, planned) | Yes | Already session fields today; #27 only adds ways to enter them. |
| **Lock Screen fold and Undo** (#29, planned) | The resulting **hands** sync like any other hand | The fold toggle and the undo record stay on the device. |
| **Tournament fields** (#8, future) | Room reserved | Sessions must be able to carry a session kind (cash, tournament, sit-and-go; the game-type enum already has these) plus tournament-only details (buy-in plus fee, entrants, finishing place, payout, bounties, multi-day) without a later migration of existing users' data. Max decides how. |

**Stays on the device (never synced):**
- Sign-in tokens (Keychain).
- The auto-restore flag.
- Live Activity state.
- The hand logger's in-progress state.
- The planned "Fold button on Lock Screen" toggle (#29) and the quick-fold undo record.
- The planned "Show live P/L on Lock Screen" toggle (#30). It's per device on purpose: one phone may be used at the table and another at home.
- The DEBUG "Seed test data" output. It must never sync from a release build, and should be blocked from syncing in debug builds too unless explicitly allowed.

**Derived data:** stats are computed from sessions and hands; the stats themselves aren't synced. Section 12 covers keeping iOS and web numbers identical.

## 7. Offline-first behavior

1. **The device is always usable.** Every action works with no connection and is saved on the device immediately: start or end a session, log, delete or undo a hand, edit, rebuy. The UI never waits for the server.
2. **Changes queue.**
   - Each local change goes into an outgoing queue that survives the app being killed, the phone rebooting, and days offline.
   - The queue sends changes in the order they were made.
   - A change counts as synced only once the server confirms it.
3. **When sync runs:**
   - At launch and when the app comes to the foreground.
   - Shortly after local changes while online, batched, so a fast run of folds doesn't mean one request per tap.
   - When connectivity returns.
   - Background refresh is best-effort and isn't relied on.
4. **The hand logger is never slowed down.** No network call, spinner or sync status appears in the logging path. A Lock Screen fold (#29) only writes locally and queues.
5. **Receiving changes.** Changes from other devices merge in without moving the user off the screen they're on. If the session being viewed changed elsewhere, a small notice appears: "Updated on another device."
6. **Long offline periods.** Weeks offline must work. When the device reconnects it sends its queue and then catches up. Conflicts resolve as in section 8.
7. **Status, never blocking.** Settings > Sync shows the state (copy in section 13). Elsewhere, at most a small indicator when there's a problem the user can fix.
8. **Signed out or never signed in.** Nothing is sent. With no owner marker (never signed in), nothing is queued and data stays local (sections 3 and 10). Once the device has an owner marker (section 9.4), changes are queued on the device whether signed in or not, and pushed only while the signed-in account matches the owner.

## 8. Conflicts the user sees

The basic rule: **the most recent change to each field wins.** When sessions differ, both are kept. Deletes win over edits, but deleted items can be recovered for a while. Users should almost never see a dialog.

### 8.1 Editing the same session on two devices
- Different fields (e.g. notes on phone A, cash-out on phone B): both edits are kept.
- The same field: the edit made **last** (by when the user made it, not when it reached the server) wins on every device.
  - A device whose edit lost shows "Updated on another device" if that session is open.
  - Notes: the later edit wins. Open question 5 asks whether the losing text should be kept somewhere instead.
- Hands: hands are almost always added, not edited, so two devices adding different hands to an ended session keep both. Editing the same hand works field by field, like sessions.

### 8.2 Deleting on one device while editing on another
- **Delete wins.** If phone A deletes a session (or hand) and phone B edits it, before or after, the item stays deleted everywhere.
- When phone B next syncs, if the item was open it closes with the notice: "This session was deleted on another device. You can restore it from Recently Deleted for 30 days."
- **Recently Deleted:** deleted sessions, with their hands, stay recoverable from Settings > Sync > Recently Deleted for 30 days, on any device, then are removed for good. A restored session comes back with its latest edits, including phone B's. (30 days is a proposal; open question 6.)
- Deleting a single hand isn't offered for recovery in 1.1. In-app delete is a swipe on a recent hand, and the Lock Screen has its own Undo (#29).

### 8.3 An active session on two devices
The app assumes one active session at a time today (it picks the newest active one). Sync keeps that.

- **One logging device per active session.**
  - The device that starts a session is its logging device. Only it logs hands, rebuys and stack checks, and shows the Live Activity.
  - Other devices show the session live (timer, hands, invested) with a banner: "Logging on [device name]. Log here instead?"
  - Tapping it, and confirming, moves logging to this device. The old device switches to the read-only banner as soon as it syncs.
  - Why: two devices logging into one session at once would fight over hand numbers and the auto-position button, which moves after every hand.
- **Taking over while the old device is offline.** It's allowed after the warning: "[device name] hasn't synced for 2 hours. Hands logged there since then will be added when it reconnects." When the old device reconnects:
  - its queued hands are added;
  - all hands in the session are put in time order and renumbered;
  - it then becomes read-only for that session.
- **Two sessions started offline on two devices.** Both are kept: they're different sessions. If both are still active after syncing, each device shows "You have 2 active sessions" with a choice of which to continue. Ending one doesn't affect the other.
- **Ending.** The session ends with the cash-out from whichever device ends it. If two devices end it differently while offline, the later end wins (section 8.1), and the other device shows "Updated on another device."

### 8.4 Settings
Field by field, latest change wins. No notice; the changes are low-stakes.

### 8.5 Different app versions
- A device on an older app version must never erase data it doesn't understand (e.g. stack checks from #30 or tournament fields from #8).
- If the data format changes in a way an older version can't handle, the older version stops syncing, keeps working locally, and shows "Update PokerStats to keep syncing." It never overwrites newer data.

## 9. Moving existing users into sync

### 9.1 Backup users (signed in on 1.0)
On the first 1.1 launch while signed in:

1. If the account has **no sync data yet** on the server:
   - The device's local data becomes the account's first sync data and is uploaded in the background.
   - If the device's local data is empty, the app instead starts the account from the **latest backup**. This replaces today's auto-restore, with the same rule that it only fills an empty device and never overwrites local data.
2. If the account **already has sync data** (e.g. another iPhone moved over first), the device does a first sync merge (section 9.3).
3. Progress shows in Settings > Sync, and the app stays usable throughout. Copy: "Setting up sync. Uploading 1,240 hands..."

**The old backup files:**
- 1.1 **stops making new snapshot backups** for accounts that are syncing. Sync is the cloud copy.
- Existing snapshots in `backups/{userId}/` are **kept read-only for 90 days** after the account's first successful sync, as a safety net, then deleted automatically. (90 days is a proposal; open question 1.)
- During that window, Settings > Sync > Old Backups lists them, with "Restore" (asks whether to replace or combine) and "Delete".
- Delete Account removes them immediately (section 10.2).
- Snapshots from a version-2 backup format must never be created. #30 no longer needs one (its stack checks sync as records).

### 9.2 Users who never signed in
- Nothing changes until they choose "Turn on Sync" and sign in. Then all local data uploads as the account's first data (or merges, section 9.3).
- Sync status explains the trade-off before sign-in: "Sync keeps your sessions on all your iPhones and on the web. Your data is stored on PokerStats' servers (Supabase) and is private to your account."

### 9.3 First sync when both the device and the account have data
Example: a second phone that already had a few local sessions, or a phone restored from a backup and then used.

- Records that are the same item (same ID, e.g. both came from the same backup) are merged as in section 8.1.
- Records that only exist on one side are kept. The result is the union.
- Before the merge, a one-time screen: "This iPhone has 12 sessions. Your account has 140. Combine them?"
  - **Combine** (default): keep everything.
  - **Use account data only**: replaces this iPhone's local data, with a second confirmation that names the number of sessions that will be removed from this iPhone.
  - **Not now**: sync stays off on this device.

### 9.4 Data that may belong to someone else (#69)
- The app remembers which account the local data belongs to.
- If a different account signs in on a device with local data from another account, or from no account with a previous account's marker, **nothing is uploaded until the user chooses**:
  - "Add to this account"
  - "Keep on this iPhone only" (sync stays off for that data)
  - "Delete from this iPhone"
- The same account signing back in continues as normal.
- Local data that never belonged to any account (a never-signed-in user turning on sync) goes through section 9.2 or 9.3 without this prompt.

## 10. Delete All Data, Sign Out, and Delete Account

### 10.1 Delete All Data (Settings), signed in and syncing
This decides #77 for syncing users; the owner should confirm. Two clearly separate choices, with no default:

- **"Delete from all devices"**
  - Deletes every session, hand and setting from the account on the server. Other devices remove them on their next sync. The web (1.2) shows nothing.
  - **Needs a connection.** If offline: "Connect to the internet to delete data from all devices." Nothing is deleted halfway.
  - Also deletes the old backup files (section 9.1) and empties Recently Deleted. Nothing can bring the data back.
- **"Remove from this iPhone"**
  - Clears local data and **turns sync off on this iPhone** (otherwise sync would bring it straight back).
  - The account and other devices keep everything. Turning sync back on downloads it again.
- **Not signed in:** behaves as today (clears this iPhone only), and auto-restore stays blocked (`AutoRestoreFlag`).

### 10.2 Delete Account (App Review 5.1.1(v))
Today's flow (#20, #23, #59): re-confirm with Apple, the server deletes the backups, `backup_metadata`, the profile and the auth user and revokes the Apple token, and the local wipe happens only after the server confirms. That stays. In 1.1 the server also deletes:
- all synced sessions, hands, settings, stack checks and table setups;
- everything in Recently Deleted;
- all old backup files.

**Other devices:** on their next contact with the server they learn the account is gone. They:
- sign out;
- remove that account's synced data from the device;
- show: "Your PokerStats account was deleted from another device. Its data has been removed from this iPhone."

The device can't upload anything after deletion. If a device was offline with unsynced changes, those changes are discarded with the account. (Open question 7: whether to offer exporting them first.)

**Delete Account from the web (1.2)** must behave the same. The App Store requirement applies to the iOS app, but users will expect parity.

### 10.3 Sign Out
- Signing out stops sync on that device. Changes made while signed out stay queued on the device and are sent only when the same account signs back in. Local data is handled per #69 (section 9.4).
- Unsynced changes: if the outgoing queue isn't empty, warn first: "3 changes haven't synced yet. Sign out anyway? They'll stay on this iPhone." The changes are never silently uploaded to the next account.

## 11. Privacy defaults

1. **Private by default.** Synced data is visible only to the signed-in account. Nothing is visible to other users. There are no public profiles, sharing or leaderboards in this release.
2. **Future features are opt-in.** 1.1 sharing and 1.3 leaderboards must each be explicit choices, scoped to what the user picks. They must never read a user's synced data without that choice.
3. **Honest copy.** Data is encrypted in transit and at rest by the hosting provider, but it isn't end-to-end encrypted, and the service operator can technically access it.
   - Replace "Backups are encrypted and stored securely in the cloud. Only you can access your data." (`BackupSettingsView`, flagged in #75 and #81).
   - Proposed copy: "Your sessions are stored on PokerStats' servers so they can sync. They're private to your account and never shown to other users."
   - The privacy policy (#54, #72) must describe sync, what's stored, retention (Recently Deleted, old backups) and deletion.
4. **Minimize what's stored.**
   - No location tracking. Location is the free text the user types.
   - No analytics or ad identifiers in sync.
   - Seat names in table setups are third-party data (open question 4).
5. **Never-signed-in users** send nothing to the server.

## 12. Stats parity between iOS and web

- **Requirement:** for the same account data, every stat the iOS app shows must equal what the web app (1.2) shows, to the displayed precision. That covers total and per-session P/L, hourly rate, ROI, hours, session count, VPIP, PFR, fold to 3-bet, c-bet, WTSD, W$SD, per-position stats, the Trends series, and Leak Finder ratings.
  - Same rules for what counts: only completed sessions count toward money stats, and rounding is the same.
  - The same definitions for planned changes: tips (#27; the definition of "before tips" vs net is still an open decision), stack checks (#30), tournaments (#8).
- **Today:** stats are computed on the device by pure functions (`StatCalculator`, `TrendCalculator`, `LeakFinder`, and separately in the home-screen widget).
- **Acceptance:** a shared set of reference datasets with expected values, checked on iOS and web in CI.
- **Open question for Max (open question 2):** where stats are calculated. Options:
  - on the server, for both apps;
  - in each app, from one shared spec and test fixtures;
  - a mix (e.g. server for leaderboards in 1.3, each app for its own screens).
  - The iOS app must still show correct stats offline.

## 13. Failure states and copy

All errors are plain language with a next step. Status lives in Settings > Sync, under the account.

| State | Where | Copy |
|---|---|---|
| Synced | Settings > Sync | "Synced just now" / "Last synced 5 min ago" |
| Syncing | Settings > Sync | "Syncing 12 changes..." |

| Sign out with unsynced changes | Alert | "3 changes haven't synced yet. Sign out anyway? They'll stay on this iPhone." |

No sync error ever blocks logging hands or starting or ending a session.

## 14. Acceptance criteria (testable)

1. **Two-device sync.** With phones A and B signed in to one account and online, a session ended on A, with 50 hands, appears on B with identical fields and hands within 60 seconds of B coming to the foreground.
2. **Offline.** In airplane mode, start a session, log 300 hands, edit notes, end the session, then kill and relaunch the app. Nothing is lost. After reconnecting, all of it reaches the server and the other device, and the outgoing queue empties.
3. **Logging speed.** Hand logging taps and timing are unchanged from 1.0 online, offline, and while a large first sync is uploading.
4. **Field conflict.** Notes edited on A at 10:00 and on B at 10:05, both offline, then both reconnect: both devices show B's notes. Cash-out edited only on A is kept.
5. **Delete versus edit.** Delete on A, edit the same session on B offline, reconnect: deleted on both. B shows the deleted-elsewhere notice. Restoring from Recently Deleted within 30 days brings it back with B's edit. After 30 days it's gone and can't be restored.
6. **Active session.** A starts a session. B shows it read-only with the "Logging on..." banner. Take over on B, log 10 hands, reconnect A: A is read-only, the hand numbers are continuous and in time order, and auto-position continues correctly on B.
7. **Two offline sessions.** Sessions started on A and B while both are offline: after sync, both exist, and each device offers the choice of which active session to continue.
8. **Backup migration.**
   - An account with backups and no sync data, on a device with local data: local data becomes the account's data, with no duplicates.
   - On an empty device: the latest backup becomes the account's data.
   - Old backup files stay listed and restorable for 90 days, then are deleted.
   - No new snapshot backups are created after the first sync.
9. **First sync merge.** A device with 12 local sessions and an account with 140 (2 shared IDs): "Combine" gives 150, and "Use account data only" leaves 140 on the device after a second confirmation.
10. **Other account's data (#69).** Account A's data on a device, sign out, account B signs in: nothing is uploaded before the user chooses, and each choice does what it says.
11. **Never signed in.** No network requests carrying poker data are made, and every feature works.
12. **Delete All Data.**
    - "Delete from all devices": server data, Recently Deleted and old backups are gone, and the other device is empty after its next sync. Offline, the option refuses with the copy above and nothing is deleted.
    - "Remove from this iPhone": the device is empty, sync is off there, and the account and other devices are unchanged.
13. **Delete Account.** Server sync data, old backups, profile and auth user are deleted, and the Apple token is revoked (existing #20 behavior). This device is wiped only after the server confirms. The other device signs out, removes the data, and shows the notice.
14. **Older app version.** A device on an older version never deletes or blanks fields it doesn't know. When the format is incompatible, it shows the update copy and stops syncing.
15. **Privacy.** A second account can't read the first account's data by any means the apps or the public API offer (Max to specify the test). The privacy copy and policy match section 11.
16. **Stats parity.** The reference datasets give identical stats on iOS and web (enforced once 1.2 exists; iOS is checked against the fixtures from 1.1).
17. **Tournament room.** The design shows how a tournament session (#8) would be stored and synced without migrating existing users' data. Reviewed in Max's design, not built in 1.1.

## 15. Open questions for the owner (and Max where marked)

1. **Old backups:** keep the old snapshot files read-only for 90 days after first sync, then delete them? Or delete them immediately after a verified sync, or keep them until the account is deleted?
2. **Stats location (Max):** where are stats calculated: on the server, in each app from a shared spec with test fixtures, or a mix? The iOS app must still work offline.
3. **Taking over an active session:** allow taking over from a device that's offline (with the warning), or only when the other device is reachable?
4. **Seat names in table setups:** these are names of other players. Sync them (private to the account), strip them before syncing, or make it a setting?
5. **Losing notes edits:** the latest notes edit wins. Keep the losing text somewhere (e.g. appended, or in a history), or discard it?
6. **Recently Deleted:** 30 days, a different period, or no Recently Deleted in 1.1?
7. **Delete Account with unsynced changes on another device:** discard them silently with the account (current proposal), or offer an export first?
8. **End-to-end encryption:** confirm it's out of scope (it blocks web and leaderboards), and approve the privacy copy in section 11.
9. **#77 for syncing users:** confirm the two-choice Delete All Data in section 10.1.
10. **Device names:** show the iPhone's name ("Rohan's iPhone") in "Logging on..." banners, or a generic "your other iPhone"? The device name is personal data shown only to the same account.
11. **Sharing:** 1.1 is "Sync + sharing". Confirm sharing gets its own spec, and that nothing in sync is shared by default.
