## 1. Decisions in one place

1. **Postgres tables, one row per record.** Sessions, hands and settings become rows keyed by the IDs the app already generates. No more snapshot files for syncing accounts.
2. **Clients write patches.** A push carries only the fields the user changed. Patches are applied in the order the server receives them, so different fields edited on two devices are both kept, and for the same field the last one received wins.
3. **The server owns time and order.** Every write gets `server_updated_at` (server clock) and a per-user `revision` (a counter). Device clocks are never used to resolve a conflict (#110.3).
4. **Deletes are tombstones.** `deleted_at` is set and never cleared by an edit. Edits to a deleted row still apply, so a restore brings back the latest edits (spec 8.2). After 30 days the row is purged to a stub.
5. **Wipe epoch.** "Delete from all devices" bumps a per-user epoch. Pushes made against an older epoch are rejected, so an offline queue can't undo a wipe (#110.2).
6. **Ownership is enforced by the database.** Every table has `user_id references auth.users on delete cascade`, RLS on `auth.uid()`, and composite keys so a hand can only point at its owner's session. Account deletion removes everything by cascade, and writes after deletion fail (#110.4).
7. **Stats are computed in each app** from one shared definition and shared golden fixtures. The server computes only what must not be trusted to clients (1.3 leaderboards), through aggregate views (section 10).
8. **Backup migration is client-driven.** No server job parses users' backup files. The app that already reads them uploads the data as ordinary inserts.

## 2. Tables

All tables live in `public`. All timestamps are `timestamptz` in UTC. `id` values are the app's existing UUIDs (`Session.id`, `Hand.id`).

Columns every synced table has (called "sync columns" below):

| Column | Type | Set by |
|---|---|---|
| `user_id` | `uuid not null references auth.users(id) on delete cascade` | Trigger, always `auth.uid()`. A client-supplied value is overwritten. |
| `revision` | `bigint not null` | Trigger, from `sync_state.revision` (section 4.2). The purge sets it for the row's user (section 5.3). |
| `server_updated_at` | `timestamptz not null` | Trigger, `now()` |
| `deleted_at` | `timestamptz` | Push `delete` op (server time). Cleared only by a `restore` op. |
| `purged_at` | `timestamptz` | Purge job (section 5.3) |
| `updated_by_device` | `uuid` | Trigger, from the push |

## 3. Row-level security and grants

### 3.1 Policies

Every table in section 2 gets, in the same migration that creates it:

- `enable row level security`, on every table including `sync_config`.
- A `select` policy `using (user_id = auth.uid())` on every table with a `user_id`. `sync_config` has no `user_id`; its policy is `select to authenticated using (true)`.
- An `insert` policy `with check (user_id = auth.uid())` and an `update` policy with `using` and `with check (user_id = auth.uid())`, on tables clients write (`poker_sessions`, `hands`, `user_settings`, `devices`).
- No `delete` policy and no delete grant on synced tables. Deletes are tombstones; hard deletes happen only in the purge job, the wipe function and the account cascade. A client issuing a raw `DELETE` can't remove a row that other devices would then never hear about.
- `sync_state` and `sync_config`: select only.
- `anon` gets no grants on any of these tables. Supabase's default privileges grant more than this, so #84 revokes explicitly (section 3.5).

### 3.2 Writes only through the push RPC

Clients keep `insert`/`update` grants (the RPC is `security invoker`, so it writes as the caller and RLS applies). To stop raw PostgREST writes that would skip the epoch and protocol checks, the `BEFORE INSERT OR UPDATE` trigger on each synced table requires `current_setting('pokerstats.push', true) = 'on'`, a transaction-local setting that only `sync_push` sets (`set_config('pokerstats.push', 'on', true)`). Otherwise the trigger raises. `set_config` is not reachable through PostgREST, which only exposes the `public` schema.

The check compares to the value `'on'`, never `is not null`. After a transaction-local `set_config` ends, the setting reads `''` (not NULL) for the rest of that pooled connection's life, so a null check would let the next raw write on that connection through. Test (SQL, one session, so the connection is the same): run `sync_push` in its own committed transaction, then do a raw `insert` and a raw `update` as the same user in a second transaction; both must raise. This file can't use the usual `supabase test db` begin/rollback wrapper, because inside one transaction the `'on'` that `sync_push` set is still active and the raw write would pass. It cleans up its own rows.

The trigger also overwrites `user_id`, `revision`, `server_updated_at` and `updated_by_device`, refuses to change `deleted_at` or `purged_at` except through the op that owns them, and rejects an update that changes `hands.hand_number` to a different value (`new.hand_number is distinct from old.hand_number`). Two devices restored from one backup (7.1) and the Old Backups import (7.2) resend the same value, and rejecting the key would drop the change's other fields. The client sends `hand_number` only on create. The only other path through the trigger is the purge (section 5.3).

`devices` has no sync columns, so it gets its own trigger, `sync_private.devices_guard()`, with the same push-setting check. Without it, a raw PostgREST write could raise the user's own `last_applied_seq` and make that device's later changes silently skipped.

### 3.3 Functions

Per Kate's rules: views and RPCs are `security invoker`; `security definer` only where the body is filtered on `auth.uid()`. Every function sets `search_path = ''` and schema-qualifies every name. No function body uses dynamic SQL (`execute`, `format()`).

Helpers that only the trigger or `sync_push` call live in `sync_private`, a schema PostgREST does not expose, so they have no `/rpc` endpoint. `public` holds only what the app calls.

| Function | Mode | Why |
|---|---|---|
| `public.sync_push(payload jsonb)` | invoker | All client writes (section 4) |
| `public.sync_wipe()` | definer, `where user_id = auth.uid()` on every statement | Hard-deletes the caller's rows and bumps the epoch (section 6.1) |
| `sync_private.next_revision()` | definer, `where user_id = auth.uid()` | Clients can't update `sync_state`; the trigger needs to bump it |
| `sync_private.mark_first_sync()` | definer, `where user_id = auth.uid()` | Sets `first_sync_completed_at` once. Called by `sync_push` when the push carries `"first_sync_done": true` (section 7.1). |
| `sync_private.row_guard()` | invoker, trigger | Section 3.2 |
| `sync_private.devices_guard()` | invoker, trigger | Section 3.2. Covered by the revokes and the grants test in 3.5 like every other function here. |
| `sync_private.purge_expired()` | invoker, run by `pg_cron` as `postgres` | Section 5.3. `execute` revoked from everyone else. |
| `public.handle_new_user()` | existing definer trigger, keyed on `new.id` | Also inserts `sync_state`. Its `search_path` is `public` today; #84 pins it to `''` and schema-qualifies its body. |

`authenticated` gets `usage` on `sync_private` and `execute` on `next_revision` and `mark_first_sync` only, because the trigger and `sync_push` run as the caller. Without PostgREST exposure, the only way to reach them is from SQL already running inside those functions.

### 3.4 Cross-user tests (Kate's gate, #110.1)

Run against a local Supabase in CI (`supabase start`, then Deno tests with two signed-in test users A and B and an anon client). For **every** table in section 2, as B, against rows A owns:

1. `select` returns zero rows, including by A's exact `id`.
2. `update` through `sync_push` with A's IDs changes nothing in A's rows (B gets its own new row with the same `id`, under B's `user_id`; A's row is unchanged).
3. A raw PostgREST `insert`, `update` or `delete` fails, even for B's own rows (section 3.2).
4. Inserting with `user_id` set to A results in a row owned by B.
5. A hand from B that names A's `session_id` fails the composite foreign key.
6. `sync_wipe()` as B leaves A's row count unchanged.
7. The anon client can't select, insert or call any RPC.

Plus: `sync_state` and `sync_config` reject every write from A and B; `devices` follows 1 to 4. The test list is the checklist for adding `stack_checks` and `tournament_details` later.

These tests go through the trigger, which rejects raw writes and overwrites `user_id` before `with check` runs, so they can pass with a broken policy. A second set tests the policies alone, as SQL (pgTAP through `supabase test db`), one file per table. In a transaction that is rolled back: as the table owner, disable the `row_guard` trigger; then `set local role authenticated`, set `request.jwt.claims` to B's `sub`, and set `pokerstats.push` to `'on'`. As B, against A's rows:

1. `select`, including by A's `id`, returns zero rows.
2. `update ... where id = <A's id>` affects zero rows.
3. An `insert` with `user_id` = A raises the `with check` violation.
4. Updating B's own row to `user_id` = A raises the `with check` violation.

Also SQL-level: the pooled-connection test in section 3.2, the grants test in section 3.5 and the Realtime test in section 4.6.

### 3.5 Grants

Supabase's default privileges give `anon` and `authenticated` `ALL` on new tables in `public` (including `DELETE` and `TRUNCATE`) and `EXECUTE` on new functions. #84 revokes in the same migration, per object:

- `revoke all on <every table in section 2> from anon`.
- `revoke delete, truncate, references, trigger on <every table in section 2> from authenticated`.
- `revoke insert, update on sync_state, sync_config from authenticated`.
- `revoke execute on <every function in section 3.3> from public, anon, authenticated`, including `sync_push`. Supabase's defaults grant `execute` to `authenticated` directly, so revoking from `public` alone isn't enough. Then grant `execute` back to `authenticated` only on `sync_push`, `sync_wipe`, `next_revision` and `mark_first_sync`. That gives the grants test an exact expected state.
- `revoke all on schema sync_private from public, anon`.

A pgTAP test checks the result with `has_table_privilege` and `has_function_privilege` for `anon` and `authenticated`, so a later migration that re-grants fails CI.

## 4. Sync protocol

### 4.1 Push

`rpc/sync_push` with:

```json
{
  "protocol": 1,
  "device_id": "uuid",
  "app_version": "1.1 (2026...)",
  "epoch": 0,
  "changes": [
    { "seq": 41, "op": "upsert", "table": "hands", "id": "uuid",
      "fields": { "session_id": "uuid", "preflop_action": "fold", "position": "BTN", "played_at": "2026-10-18T02:11:09Z", "hand_number": 17, "faced_3bet": false } },
    { "seq": 42, "op": "upsert", "table": "poker_sessions", "id": "uuid", "fields": { "notes": "tight table" } },
    { "seq": 43, "op": "delete", "table": "hands", "id": "uuid" }
  ],
  "first_sync_done": false
}
```

Rules, checked in this order, for the whole batch:

1. `protocol < sync_config.min_protocol` returns `upgrade_required`. Nothing is written.
2. No `sync_state` row for `auth.uid()` returns `account_missing` (deleted between token issue and now).
3. `epoch < sync_state.wipe_epoch` returns `wiped`. Nothing is written.
4. Changes with `seq <= devices.last_applied_seq` are skipped as already applied.

The envelope must be readable and within the limits below, or the whole batch returns `invalid` and nothing is written.

Then each change, in `seq` order:

- **`table`** is matched against a fixed allowlist: `poker_sessions`, `hands`, `user_settings` (`stack_checks` joins with #30). Each name maps to its own static SQL statements. The client string is never put into SQL. An unknown table rejects that change (`unknown_table`). `devices` is not a change target; `sync_push` writes it from the envelope.
- **`fields`** may only contain the client columns of that table. A sync column or an unknown key rejects the change.

- **`upsert`**: insert the row if `(user_id, id)` doesn't exist, otherwise apply only the keys in `fields` (`jsonb_populate_record` over the current row). Keys not in `fields` are never touched. A row with `purged_at` set ignores all ops (result `purged`). So does a hand (and later a stack check) whose parent session has `purged_at` set (section 5.3).
- **`delete`**: set `deleted_at = now()` if not already set. Deleting a session tombstones the session only; its hands are hidden by the client and purged with it.
- **`restore`**: clear `deleted_at` if the row is not purged.

Edits to a tombstoned row still apply (delete wins for visibility; the restore shows the newest data). The batch is one transaction; `devices.last_applied_seq` and `last_seen_at` advance in it.

Each change runs in its own `begin ... exception` block, which is a savepoint. A constraint error in one change (the composite foreign key, a check, a bad type) rolls back that change only and returns `rejected` with the SQLSTATE as `reason`; the rest of the batch applies. `last_applied_seq` advances past rejected changes too, so a retry doesn't run them again. Without this, one bad change fails the batch, and dropping an `invalid` batch would lose up to 499 valid changes. Note for #84: 500 savepoints in one transaction exceeds Postgres's 64-entry subtransaction cache. Correctness is unaffected; if load tests show the slowdown, lower the batch limit.

Limits:

| Limit | Value (proposed) | Enforced by |
|---|---|---|
| Payload size | 1 MB (`octet_length(payload::text)`) | `sync_push`, after the batch rules above; `invalid`. This caps what `sync_push` processes. PostgREST has already read and parsed the body by then, so it is not request-size protection. |
| Changes per push | 500 | `sync_push`; `invalid` |
| `notes` (sessions, hands) | 10,000 characters | Column `check`; `rejected` |
| `location`, `stakes`, `default_stakes` | 200 characters | Column `check`; `rejected` |
| `currency` | 8 characters | Column `check`; `rejected` |
| `table_config` | 16 KB (`pg_column_size`) | Column `check`; `rejected` |
| Rows per user (optional) | 50,000 sessions, 500,000 hands | `sync_push` on insert; `rejected` (`row_cap`) |

Column checks apply on every write path, not only the RPC. The row cap is optional for #84.

Response: `{ "status": "ok", "revision": <sync_state.revision>, "results": [{ "seq": 41, "result": "applied" | "skipped" | "purged" | "rejected", "reason": "..." }] }`. Non-ok statuses: `upgrade_required`, `wiped`, `account_missing`, `invalid` (an envelope the server can't read or that breaks a batch limit; per-change errors are `rejected` instead. The client logs and drops the batch to avoid a stuck queue, after a fixed retry count).

### 4.2 Order and clock

`sync_private.next_revision()` does `update public.sync_state set revision = revision + 1 where user_id = auth.uid() returning revision`. The row lock it takes is held until the push commits, so one user's pushes are serialized and revisions commit in increasing order. That is what makes the pull cursor gap-free. Different users never contend.

"Last write wins" means last committed push. A device that was offline for a week and reconnects after another device's edit will overwrite that field. That is a change from spec 8.1, which ranks by when the user made the edit; owner question 1.

### 4.3 Pull

1. Read `sync_state` (`revision` as `high`, `wipe_epoch`). No row means `account_missing`, not an empty server: for a deleted user with a still-valid JWT, PostgREST returns zero rows, not an error. Treating it as empty would start the 7.1 step 2 upload.
2. If `wipe_epoch` is newer than the device's, run the wiped path (section 6.1) instead.
3. For each table: `select * where revision > :cursor and revision <= :high order by revision limit 1000`, paging by `revision`.
4. Apply locally, then store `cursor = high` and `epoch = wipe_epoch`.

RLS limits all of this to the caller's rows. Pulls go straight to PostgREST; no RPC. A row's revision is unique per user (pushes and the purge take one per row), so paging by `revision` never splits a page.

### 4.4 Idempotency

Each device numbers its queued changes with a strictly increasing `seq`. If a push commits but the response is lost, the retry is skipped by `last_applied_seq` instead of replaying an old value over a newer one.

- **Coalescing.** The client may merge an unsent change into the latest unsent change for the same `(table, id)`, with the union of their fields (later values win), only when both have the same `op`. An upsert never absorbs a `delete` or `restore` that follows it, and nothing merges across one, so a tombstoned row uploaded as an upsert then a `delete` (section 9.3) stays two changes. The merged change takes the highest `seq`, except when it merges into a queued insert (the full upsert enqueued when the row is created, or by re-enable step 2): then it keeps the insert's `seq`. Otherwise ending a session whose insert is still queued would move it after its hands, and the hand inserts would reach the server before their session. Keeping the earlier `seq` is safe under `last_applied_seq` because pushes go in `seq` order and changes already in a push that is in flight are never merged. `addHand` rewrites `table_config` on every hand, so coalescing keeps the queue small.
- **`deviceId` and `nextSeq` survive same-account resets.** Delete All Data, Remove from this iPhone, Delete from all devices and `wiped` empty only the queue. `nextSeq` keeps increasing and never goes back, so `last_applied_seq` never skips a new change. A new `deviceId` (with `nextSeq` 0) is made only when the account changes: account deleted, the #69 switch (including "Add to this account", which also empties the queue, section 9.3), or adoption by a different user after a reset that cleared the marker. `SyncMeta.deviceIdUserId` records the account the ID was issued under, and adoption by any other account makes a new ID, so one device ID is never stored under two `user_id`s on the server. A new ID on every reset would leave a dead `devices` row each time, and re-adding the phone mid-session would make its own active session read-only, since `logging_device_id` would name the old ID.

### 4.5 When sync runs

As spec 7.3: launch, foreground, a few seconds after local changes (batched), and on reconnect. Push before pull. Nothing in the hand-logging path awaits the network. The push loop is suspended while Delete Account runs on this device, as #132 does for backups (`AuthService` on #132), and before every local reset (section 9.8).

### 4.6 Realtime

Not used in 1.1. The synced tables are not added to the `supabase_realtime` publication, and a pgTAP test checks `pg_publication_tables` for them. If they are ever added, RLS applies to subscriptions, and a cross-user subscription test is required in the same PR.

## 5. Conflicts and deletes

### 5.1 Summary

| Case | Result |
|---|---|
| Two devices edit different fields of one row | Both kept (patches touch only their own keys) |
| Two devices edit the same field | The push the server commits last wins |
| Delete on A, edit on B (either order) | Stays deleted; B's edit is stored and returns on restore |
| Two devices create rows | Both kept (distinct UUIDs) |
| Old app version | Never sends fields it doesn't know, so it can't blank them (spec 8.5); below `min_protocol` it stops pushing |

### 5.2 Active session

`logging_device_id` is an ordinary field. Taking over is a patch to it. Hands pushed later by the old device are still accepted (spec 8.3); the old device sees the new `logging_device_id` on its next pull and goes read-only. The server does not reject hands from a non-logging device, because offline hands must be kept.

### 5.3 Purge

A daily `pg_cron` job runs `call sync_private.purge_expired()` as `postgres`, for rows with `deleted_at < now() - interval '30 days'` and `purged_at is null` (spec OQ6). There is no `auth.uid()` in the job, so `next_revision()` would bump nothing. The purge takes revisions itself, per user, one transaction per user. A function called by `pg_cron` runs in one transaction, so `purge_expired` is a procedure that `commit`s after each user:

1. `set_config('pokerstats.purge', 'on', true)` at the start of each per-user transaction. The setting is transaction-local, so it is gone after each `commit` and must be applied again.
2. For each row: `update public.sync_state set revision = revision + 1 where user_id = <row's user_id> returning revision`. This is the same row lock a push takes, so the purge and that user's pushes serialize and the pull cursor stays gap-free.
3. Hard-delete a purged session's hands. Devices already hide them, and the session stub tells devices to drop them.
4. Replace the row's data columns with stub values, set `purged_at = now()` and `revision` to the value from step 2, keeping only the key and sync columns. Stub values respect the not-null columns: text columns `''`, money `0`, nullable columns null, `start_time` and `played_at` `'1970-01-01T00:00:00Z'`, `faced_3bet` false, `hand_number` 0.

The trigger (section 3.2) accepts this path only when `current_setting('pokerstats.purge', true) = 'on'` and `current_user = 'postgres'`. In that mode it keeps `user_id`, the key and the revision the purge set, sets `server_updated_at = now()` and `updated_by_device` to null, and skips the `hand_number` rule. It does not overwrite `user_id` with `auth.uid()`, which is null under `pg_cron`. Clients can't take this path: they can't set settings and don't run as `postgres`.

The stub keeps an old offline device from recreating a purged session with a later `upsert`. The composite foreign key alone doesn't stop that device from inserting a hand under the stub, which would never be purged, so `sync_push` returns `purged` for a hand (and later a stack check) whose parent session has `purged_at` set. It holds no user content. Hands deleted one by one are purged the same way. Tests: a purged row gets a revision above a device's cursor and the next pull returns it with `purged_at` and its original `user_id`; a hand pushed into a purged session returns `purged` and is not written; one `call` purges rows for two users; calling `purge_expired()` as `authenticated` fails.

## 6. Delete flows

### 6.1 Delete from all devices (spec 10.1)

Online only. The app:

1. Deletes the old backup files and `backup_metadata` rows through Storage and PostgREST with the user's own token (existing `backups_delete_own` and `backup_metadata_delete_own` policies).
2. Calls `sync_wipe()`, which in one transaction hard-deletes the caller's rows in `hands`, `poker_sessions`, `user_settings` (and later `stack_checks`, `tournament_details`) and increments `wipe_epoch`.
3. Clears local data, stores the new epoch, and empties its queue.

Another device that pushes with the old epoch gets `wiped`: it discards its queue and local synced data, adopts the new epoch and pulls (which returns nothing). Its queued edits can never reach the server (#110.2).

Backups go first, as in delete-account. If step 2 fails after step 1, the app retries step 2; synced data is untouched until it succeeds.

### 6.2 Remove from this iPhone

Local only. Clear local data, turn sync off on this device, and clear the owner marker. With an empty store and no marker, turning sync back on adopts the signed-in account and downloads (section 9.2), so clearing it loses nothing. Section 9.8 lists every field this resets. Two conditions keep this safe:

- Any write while signed in sets the owner marker again, even with sync off (section 9.3). Otherwise A could log sessions after Remove, sign out, and B would adopt them with no 9.4 sheet.
- Turning sync back on pulls first and never re-uploads every local row (section 9.3). Uploading every row would push stale values over newer server edits: an old backup after Restore while not syncing, or the local `Settings` that Remove and Delete All Data keep.

### 6.3 Delete Account (spec 10.2)

The existing `delete-account` function is unchanged in order: Apple revoke, storage and `backup_metadata`, `profiles`, then `auth.admin.deleteUser`. Deleting the auth user cascades to `sync_state`, `devices`, `poker_sessions`, `hands`, `user_settings` and the reserved tables. #84 adds a test that a user with rows in every synced table has zero rows anywhere after the function succeeds.

After deletion:

- A still-valid JWT can't write: `sync_push` returns `account_missing`, and any insert would fail the foreign key to `auth.users` (#110.4).
- Other devices find out on their next push or token refresh (#48):
  - While their JWT is still valid: `account_missing` from `sync_push`, or `user_not_found` from `auth.user()`. These are final. The app runs the account-deleted flow (spec 10.2) and never backs off and retries. Nothing on `main` or #132 calls `auth.user()` today, so #85 calls it on launch and on foreground while signed in with sync on, and after a 401 or 403 from a push or pull. #132's `accessToken` maps every `AuthError.api` to `.refreshUnavailable` (`SupabaseClient` on #132), so #85 has to match these codes before that mapping.
  - `user_banned`, from `auth.user()` or from the refresh grant, is also final but is not a deletion. The app signs out and stops syncing, keeps local data, the queue and the owner marker, and never retries. supabase-swift 2.55.4 doesn't treat it as a cleanup code, so #85 handles it.
  - After the JWT expires: refresh never returns `user_not_found`. The refresh token went with the cascade, so Auth returns `refresh_token_not_found`, which supabase-swift 2.55.4 handles as a sign-out (`.signedOut`). That looks the same as a revoked or expired session. The app signs out and keeps local data under the old owner marker; at the next sign-in Apple creates a new `auth.uid()` and the owner check (section 9.2) decides.

## 7. Moving backup users over

Client-driven, using code that already exists (`BackupService`, `LocalDataRestorer`).

### 7.1 First 1.1 launch while signed in

1. Pull. No `sync_state` row is `account_missing` (section 4.3). If the server has rows for this user, go to the first-sync merge (spec 9.3).
2. Otherwise, if the device has local data: upload it as `upsert` batches. `Hand.session` is optional locally but `session_id` is not null, so hands with no session are skipped and logged instead of being sent and rejected. Money is rounded to cents and clamped to the `numeric(14,2)` range (`Double("1e20")` parses).
3. Otherwise, if the account has a backup: download the latest, restore it locally (the existing empty-device rule), then upload it as in 2.
4. When the upload queue is empty, send a push with `"first_sync_done": true` (an empty `changes` list is allowed). `sync_push` calls `sync_private.mark_first_sync()`, which sets `first_sync_completed_at` and `backups_retire_at` once and is a no-op afterwards.

Once sync is on, `AutoRestore` (`PokerStatsApp.swift:51-94`) never runs on its own; step 3 replaces it, and an independent run could fill an empty store alongside a pull. Auto-backup on session end (`ActiveSessionViewModel.swift:144`) stops too, or the section 7.3 policy would show "Backup failed" every time.

Because IDs come from the same backup, two devices restored from one backup and migrating in either order produce the same rows; the second one's upserts become patches with mostly identical values. No duplicates (spec 14.8).

### 7.2 Old backups

- Kept read-only until `backups_retire_at` (spec OQ1, proposed 90 days), listed in Settings > Sync > Old Backups.
- A manual restore from Old Backups imports as upserts through the repository (section 9.3), so the rows are queued and synced. It does not replace all local data the way `LocalDataRestorer.restore` does. Spec 9.1 offers "replace or combine"; this design supports combine only (section 12).
- A scheduled edge function `retire-backups` runs daily and deletes backup files and `backup_metadata` for users whose `backups_retire_at` has passed. It reuses `cleanup.ts`'s storage listing and removal and the service-role key that Supabase already injects into edge functions. Storage files have to be deleted through the Storage API, so a SQL-only `pg_cron` job can't do this.
- **Invocation.** `pg_cron` calls the function daily through `pg_net`. That call needs a credential, so the earlier "no new secret" was wrong. It needs one new secret, `RETIRE_BACKUPS_CRON_SECRET` (random, at least 32 bytes), stored in two places: Supabase Vault, where the cron job reads it, and the edge function secrets, where the function compares it. The owner generates and adds it; #84 asks for it and waits. It is not the service-role key.
- **Caller check.** `verify_jwt = true` stays. The cron request sends the project's legacy JWT anon key as the bearer token, which passes the gateway, plus an `x-cron-secret` header. `sb_publishable_` keys are not JWTs and fail `verify_jwt`, and disabling the legacy keys would break this cron. The cron command reads both values from `vault.decrypted_secrets` at run time and never inlines them in `cron.job`. `pg_net` keeps request headers in `net.http_request_queue` until sent, so #84 confirms the `net` schema isn't granted to `anon` or `authenticated`. The function compares the header to the secret in constant time and returns 401 with no deletions for anything else, so an anon or signed-in user call can't trigger deletions. Tests, with fake clients like `cleanup.test.ts`: no header, a wrong header, and a user JWT each get 401 and delete nothing.
- Delete Account and Delete from all devices remove them immediately (sections 6.1, 6.3).

### 7.3 No new snapshot backups

Enforced on the server, not only in the app: the `backups_insert_own` storage policy and `backup_metadata_insert_own` gain `and not exists (select 1 from public.sync_state s where s.user_id = auth.uid() and s.first_sync_completed_at is not null)`. The same condition is added to `backups_update_own` (`init_schema.sql:107`), so an owner can't overwrite a read-only old backup in place with `x-upsert`. 1.0 always writes new timestamped paths, so the app can't reach that today. A 1.0 build that is still installed on a second phone can't add or overwrite snapshots after the account has migrated.

## 8. Auth constraints that shape the design

- **Identity linking.** Supabase automatically links OAuth identities that share a verified email into one `auth.users` row. Sync keys everything on `auth.uid()`, so linked identities see one data set. The 1.2 web spec says "no silent merge" by email (its open question 2), which automatic linking contradicts once Google exists. Most Apple accounts use a relay address and won't match. Two settings keep linking to verified emails only: manual linking (`linkIdentity`) stays disabled in Auth, and any email provider that is ever enabled requires email confirmation. Owner question 4 covers the rest.
- **Session limits are project-wide.** Single-session-per-user, time-boxed sessions and inactivity timeouts in Supabase Auth apply to iOS and web alike. Turning any of them on for the web would sign out iPhones, and an inactivity timeout would break devices that are offline for weeks (spec 7.6). The design assumes all three stay off. Owner question 5.
- **Keys** (#110.7). iOS and web use only the publishable (anon) key. The service-role key lives only in the edge function environment (`delete-account`, `retire-backups`). No client path needs it. It never appears in `web/`, client bundles, CI output or logs, and neither does `RETIRE_BACKUPS_CRON_SECRET`. Account deletion from the web (1.2) calls the same `delete-account` function (spec 10.2), not a second implementation.

### 9.1 Local state the app adds

Cleared by every reset that empties the store (section 9.8), including Delete Account and the #69 "Delete from this iPhone" choice. Both new columns are optional with a nil default, so the 1.0 store migrates without a custom migration.

SwiftData, not App Group `UserDefaults` (iOS review): the queue entry and the `nextSeq` bump join the mutation's single `modelContext.save()`, which `UserDefaults` can't share, so a kill between them can't lose or invent a change. The widget opens the same store (`AppGroupContainer.swift:48`); the two models are added to its schema and it never reads them. Live Activities get data through ActivityKit. Deletes become tombstones locally. Today they are hard deletes (`SessionDetailViewModel.swift:66`, `ActiveSessionViewModel.swift:122-124`), so Recently Deleted would have nothing to restore. IDs are `UUID` without `@Attribute(.unique)`, and pull applies rows by fetching on `id`. If #85 adds `.unique`, it tests the migration against a 1.0 store.

### 9.2 Account checks

On sign-in, before any push:

- `ownerUserId` equals the signed-in user: continue.
- `ownerUserId` is set to another user: show the spec 9.4 sheet and push nothing until the user chooses.
- `ownerUserId` is nil: the local data never belonged to an account, because every reset that empties the store clears the marker, nothing else does, and any write while signed in sets it. Adopt the account and go through spec 9.2 or 9.3 (combine prompt if both sides have data), without the 9.4 sheet.

On the first 1.1 launch, a device that is already signed in sets `ownerUserId` to that user before anything else, so 1.0 data is attributed to the account that owned it.

On adoption, and after a local restore, active sessions with a nil `loggingDeviceId` (1.0 sessions, or a restored backup) get this device's ID locally at once, without queuing it, so an in-progress session keeps logging with no pull. The patch to `logging_device_id` is queued only after the first-sync pull confirms the server has no row for that session or its `logging_device_id` is null. If the server names another device, the pull overwrites the unqueued local stamp and the session goes read-only then, so two phones restored from one backup can't take a live session from each other. If the server row has a null `logging_device_id`, the pull writes nil over the local stamp; the re-stamp and the queued patch then happen together in the save right after the first-sync pull. A nil ID stays live until that save (section 9.5), so the null overwrite is harmless.

Spec criterion 10 cases (#110.6), as tests in #85:

- **Never signed in, then signs in:** marker nil, local data present. Adopt and upload, no 9.4 sheet. With an empty store, adopt and pull.
- **Reinstall:** deleting the app deletes the store and standard `UserDefaults`, so the marker, the queue, local data and `AutoRestoreFlag` are gone. Sign-in sees nil and an empty store, adopts and pulls. Changes that were still queued before the reinstall are lost; they were only on the device.
- **Account A's data, A signs out, B signs in:** marker A, so the sheet shows (criterion 10 as written).

Linked identities keep the same `auth.uid()`, so they never trigger the sheet.

### 9.3 Writes

Required (iOS review): every write to a synced model goes through one `@MainActor` repository. `SessionRepository` grows into it, with intent methods (`addHand`, `updateSession(fields)`, `tombstone`, `restore`, `saveSettings`, `wipeLocal`, `importBackup`). Each method mutates the model, enqueues an `OutgoingChange` with only the changed fields whenever `ownerUserId` is set, signed in or not, and saves once. With the marker nil (never signed in) nothing is queued. Sync off or signed out only pauses pushing, and the queue is pushed only while the signed-in user equals `ownerUserId`. This keeps edits made after a `refresh_token_not_found` sign-out (6.3), which the next pull would otherwise overwrite. Spec 7 item 8 and 10.3 say the same. Coalescing per `(table, id)` (4.4) keeps one entry per changed row, not one per edit (more only when a `delete` or `restore` falls between edits), so the queue grows with the number of distinct rows touched (every new hand adds one) and has no fixed cap. The resets in 9.8 still empty it. Any write while signed in sets `ownerUserId` to the signed-in user if it is nil, even with sync off. ViewModels stay `@Observable` and call the repository instead of `modelContext`; views keep `@Query` for reads. Nothing awaits the network.

**Re-enable steps**, run after every sign-in and whenever sync turns back on (after Remove from this iPhone, Delete All Data, Restore while not syncing, or a plain toggle). With the marker nil, adoption runs the same steps:

1. Pull first.
2. Upsert only local rows the server doesn't have. With the cursor at 0, the full pull has already returned every server id, so step 2 uploads every local row with no queued change that the pull didn't return, with no extra request. Above 0 (a plain toggle pulls incrementally), step 2 asks directly: for every local row with no queued change, an id-existence `select id` on that table with up to 200 ids per request. At the 500,000-hand cap (4.1) that is about 2,500 requests, which is why it runs only when the cursor is above 0. 500 UUIDs in an `id=in.(...)` filter make a URL of about 18.5 KB, so #85 keeps each request URL under 8 KB. Under RLS it returns only the caller's rows, including tombstones and purged stubs, and any id it returns is not uploaded. With queueing under the owner marker (above), a plain toggle usually finds nothing to upload, since new rows are already queued.
3. Push the queued changes.

**Adoption by a different account** (spec 9.4 "Add to this account"). The queue holds changes made under account A, some of them field-only patches to rows the new account B has never seen, and their `seq`s come from A's `deviceId`. So, in one save before the re-enable steps, the app empties the queue, makes a new `deviceId` with `nextSeq` 0 (section 4.4), sets `ownerUserId` to B, resets `epoch` and `cursor` to 0, sets `adoptionUploadPending`, and re-stamps every local active session whose `loggingDeviceId` is the old `deviceId` or nil to the new `deviceId`. Without the re-stamp, 9.5 would read the session the user is playing as logged by another device and make it read-only with sync on, and it would upload to B naming a device B has no `devices` row for. The re-stamped session goes up with the new ID in step 2's full enqueue; if B already has that session, the pull rule applies as in 9.2. Step 1 is then a full pull, and step 2, with nothing queued, covers every local row: each row B doesn't have is enqueued in full, sessions before their hands, and a locally tombstoned row is enqueued as an upsert followed by a `delete`, so it doesn't come back live under B. Rows B already has (the same ID, for example from a shared backup) take B's values under the pull rule, as spec 9.3 merges them. This was chosen over making step 2 check every local row whatever its queue state: that would still leave A's patches and `seq`s in the queue, where a patch to a row B lacks becomes an insert missing required columns (rejected, 9.6) and a high old `seq` makes B's later changes skip. Emptying the queue loses nothing for rows B lacks, because every one of them is uploaded in full. For rows B already has, signed-out edits made under A are dropped; accepted (section 12).

`adoptionUploadPending` guards a kill between step 1 and step 2. Step 1 commits the pulled rows and moves the cursor; step 2 enqueues every row B lacks in a later save, and that save clears the flag. If the app is killed in between, the queue is empty and the cursor is above 0, and the re-enable steps run only after a sign-in or a sync toggle, so B would never get those rows. On every launch with the flag set, the app re-runs steps 1 and 2. Because the cursor is then above 0, step 2 uses the id-existence query. Pushing waits while the flag is set, and on this re-run step 2 checks every local row whatever its queue state: edits made after the relaunch may have queued field-only patches to rows B lacks, and those would reach the server as inserts missing required columns. For each row B lacks, step 2 replaces its queued changes with the full upload (sessions before their hands, tombstones as an upsert then a `delete`) at new `seq`s, in the same save that clears the flag. Nothing is lost, since the full row carries every queued field.

Rows on both sides follow the pull rule in 9.5: the server wins, except for fields with a queued change. Local `Settings` is uploaded only if the server has no `user_settings` row. The full upload in 7.1 step 2 is unchanged and applies only to the first 1.1 launch, when the server has no rows.

Write sites to move today: `ActiveSessionViewModel` (add and delete hand, rebuy, end, abandon, notes, mental levels, four table-config writes), `NewSessionViewModel.createSession`, `SessionDetailViewModel.saveEdits` and `deleteSession`, `SettingsViewModel.saveSettings`, `deleteAllData` and `wipeAfterAccountDeletion`, `LocalDataRestorer`, `LocalDataWiper` and `DataSeeder`. A CI check fails if `modelContext` `insert`, `delete` or `save` appears outside the repository.

### 9.5 Reading

- Apply pulled rows by `(table, id)`. A pulled row replaces local fields except fields with a newer queued change for that row.
- Unknown enum values decode with the existing fallbacks for display, and the app never enqueues a fallback value it didn't get from the user. The exception is `status`: `Session.status` falls back to `.active` today (`Session.swift:17`), which would make an unknown status look like the live session. An unknown status decodes as completed and read-only, never active.
- `deleted_at` set: hide the row; if open, close it with the spec 13 notice. `purged_at` set: remove locally.
- Which device may log an active session:
  - Sync off, including no owner marker: a local active session is live on this device whatever its `loggingDeviceId`. So a phone with sync off can end a session another device has taken over, and on re-enable its queued `status` / `end_time` patch closes that device's live session (last write wins, no data lost). Accepted (section 12).
  - Sync on: live if `loggingDeviceId` equals this `deviceId`, or is nil until the first-sync pull decides (section 9.2). A nil the pull writes is re-stamped in the same save right after it (section 9.2). Hands logged meanwhile are queued as usual; the server accepts hands from a device that isn't logging (5.2).
  - Read-only only while sync is on and `loggingDeviceId` names another device. Two devices that start sessions offline produce two active sessions, and each device treats only its own as live (`ContentView.swift:40`, `SessionTabView.swift:14` and `SessionRepository.fetchActive` assume one). What the other device shows for it is a spec question (section 12).
- Hand numbers are derived on display: hands sort by `(played_at, hand_number, id)`, tombstones excluded, and the number shown is the position in that order. The stored `hand_number` is set on insert and never changed, so a takeover never rewrites hands and two devices never race on renumbering. Visible change: deleting a hand closes the gap instead of leaving one (Jules to confirm). No stat reads `handNumber`.

## 10. Stats location (spec OQ2)

Recommendation: **each app computes its own stats** from one written definition and shared golden fixtures (JSON datasets with expected values) checked in CI on iOS now and on web in 1.2. Reasons: iOS must work offline (so it can't depend on the server), the iOS calculators already exist as pure functions, and sending every hand to a server function adds latency for no new correctness.

The server computes only what clients can't be trusted with: 1.3 leaderboard numbers, through a `security_invoker` aggregate view that exposes totals, never sessions, and passes the same fixtures. If the 1.2 dashboard needs to avoid downloading every hand, it can use a `security_invoker` per-user aggregate view under the same RLS.
